## Method and Taxonomy

Stories are included only when a real actor can reach implemented behavior through a route, action, API route, RPC, supported app surface, or operational endpoint, and when the behavior has identifiable backing source, state, side effect, permission check, or failure state.

Coverage labels:

- `implemented+covered`: route/component plus implementation/state evidence plus matching executable test, SQL proof, or approved recorded proof.
- `implemented+manual-proof`: implementation evidence plus recorded manual/browser proof, without focused automated proof at the story seam.
- `implemented+coverage-gap`: implementation evidence exists, but proof is partial, static, mocked, smoke-only, environmental, or not rerun.
- `implemented+covered-with-sql-gap`: app behavior is covered, but SQL/RLS proof was not freshly executed in the approved lane.
- `implemented+covered-with-e2e-gap`: app behavior is covered, but browser/Playwright proof was not freshly executed in the approved lane.
- `implemented+covered-with-warning`: tests passed or proof exists with a recorded warning that limits the confidence claim.

## Evidence Gaps and Exclusions

Unsupported, partial, not-code-backed, mock-only, source-shape-only, or manual-only candidates are excluded from the main story catalog:

- Manual merchant reward-token entry is excluded. MER-12 and OPS-03 are limited to browser camera scanner/normalization and handoff to MER-13 collection.
- DSAR fulfilment/export/deletion automation is excluded. Admin privacy flows log requests and opt-outs; they do not automate export, deletion, rectification, unsubscribe fulfilment, or external email/ESP execution.
- Final legal approval is excluded. Public privacy, platform terms, and venue terms pages exist with review-required caveats, but no lawyer-approved launch claim is made.
- Browser camera/device proof remains a gap. Scanner routes and normalizers are implemented and tested, but no approved lane recorded real camera hardware proof.
- SQL/RLS and DB execution gaps remain where lane artifacts record them, including customer marketing consent SQL/RLS, audit isolation, admin write RPCs, and admin support RPC behavior.
- E2E/browser execution gaps remain where lane artifacts record them, including legal-surface Playwright coverage and admin smoke paths that were cited but not rerun in admin remediation.
- Dev/test-only surfaces are excluded from production stories: all `app/dev/**` routes, `lib/dev/**` helpers, customer-flow demo scripts, design-system catalog, preview mock data, inert preview forms, preview screenshot specs, and static proof fixtures.
- Offline loyalty mutation is excluded. PWA service worker behavior is conservative; server-state routes fall back to offline copy rather than cached stamp/reward mutation.
- Hard geofence blocking is excluded. Current customer stamp evidence is soft, cycle-aware, and non-blocking by default.
- Customer self-redeems rewards without merchant scan is excluded. Reward status is read-only; collection goes through merchant scan/token RPCs.
- Admin merchant create/edit/delete, billing refund/cancel/plan-change, fraud remediation/status update, customer profile edit/delete, audit export/search/mutation, and pilot follow-up automation are excluded.
- Staff PIN, merchant staff administration, counter-station pairing, raw customer phone export, marketing bulk messaging, external CRM/ESP consent propagation, log viewer UI, Stripe webhook ledger UI, rate-limit admin UI, and deep dependency health checks are excluded.
- Preview/mock evidence can support visual/manual QA only after production route/action/lib/SQL evidence exists; it is not used as story truth.

## Glossary

| Term                   | Meaning in this audit                                                                                                                                                      |
| ---------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Actor story            | A user-visible or operator-visible behavior reachable through implemented app, API, action, route, or operational endpoint code.                                           |
| Code-derived           | Based on implemented source, SQL, tests, public assets, or config, not on existing product prose.                                                                          |
| Covered                | The behavior has implementation evidence plus matching executable test, SQL proof, or approved recorded proof.                                                             |
| Coverage gap           | Implementation exists, but proof is limited, static, mocked, smoke-only, not rerun, or missing a needed runtime layer.                                                     |
| Drift target           | Existing prose or generated documentation that may need follow-up after this catalog because it can describe broader or older behavior than the implemented code supports. |
| Evidence gap           | A behavior that is partial, unsupported, not code-proven, environment-only, or otherwise excluded from the main implemented-story catalog.                                 |
| Forbidden story source | Existing docs, README files, micro-spec markdown, outputs, old evidence packets, and prose specs when used as source truth for a main-catalog story.                       |
| Main catalog           | The included CUS, MER, ADM, BCO, and OPS story tables above.                                                                                                               |
| Proof harness          | Dev, preview, screenshot, or test-support code that can help verify production behavior but is not itself a production story.                                              |
| Residual risk          | A known limitation that remains after this audit, such as dirty route-contract drift or missing DB/browser/provider execution.                                             |
