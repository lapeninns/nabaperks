### Important qualification on the 75.3% availability figure

The SLO number is **depressed by a measurement artifact, not by production downtime.**
Across the last seven scheduled `production-smoke` runs (30173903188, 30175789698, 30177716506,
30179669831, 30182461357, 30188305931, 30192808184) the job breakdown is identical every time:

```
Liveness and readiness            = success
Resolve recovered production alert = failure
Error to insight                   = skipped
```

The only failing step is `PRODUCTION_ALERT_WEBHOOK_URL must be a public HTTPS URL`. Production
readiness and liveness passed in **every** run. Because the SLO calculator scores whole workflow
runs, the unconfigured paging receiver drags availability to 0.753.

certification failures: the red production smoke, the SLO non-compliance, and the untestable
paging receiver.

## Defects found and fixed during this run

**D-01 — `pnpm db:reset` left the database unable to pass `pnpm test:db`.**
`supabase/reset.sql` truncated every table in `public`, including `operational_cron_jobs` — six
rows of reference data inserted by migration `20260723113000`. `seed.sql` never recreates them
and `db:migrate` is ledger-aware, so nothing restored them. `record_operational_cron_run()` then
tripped `operational_cron_runs_job_name_fkey` and `test:db` failed 297/298. Fixed by excluding
the registry from the truncate; the ledger table `operational_cron_runs` is still wiped.
Verified: 6 rows before and after `db:reset`, `test:db` 298/298. CI never hit this (it uses
`supabase start` + `db:seed`).

**D-04 — NFC square print isolation is off by 24 px on linux WebKit (found, NOT fixed).**
`tests/e2e/nfc-square-print.desktop.spec.ts` → "isolates the plate from the app shell at the
physical page origin" wraps the print root in a shell padded 320 px / 180 px, switches to print
media, and asserts the root lands at the physical page origin. On CI's linux WebKit it fails
`expect(received).toBeCloseTo(0, 1)` with **received 24**. It is consistent, not flaky: the same
test failed in both nightly runs (`3a6e8baa` unsharded and `a6d1c34f` sharded), and in the
former desktop-safari was otherwise clean at 137 passed / 1 failed.

It does **not** reproduce on darwin WebKit — run locally against `--project=desktop-safari` it
passes in 3.8 s. So this is a linux-vs-darwin WebKit rendering difference in the print box
model, the same class of platform divergence already recorded for linux Firefox `scrollHeight`.

Deliberately left unfixed. The honest options are to investigate the linux-WebKit print reset or
to accept a documented platform tolerance; loosening the assertion would weaken a gate that
exists precisely to catch print-isolation regressions, and that is an owner decision. Practical
exposure is low — real printing happens from users' own Chrome/Safari on macOS and Windows, not
linux WebKit. **B-09**

**D-03 — the unit suite needs a browser, and neither job that runs it installed one.**
`tests/unit/google-review-pdf.test.mjs` renders four assertions through a real Chromium
(`google-review-pdf` → `google-review-pdf-render` → `print-kit-browser` →
`chromium.launch()`), also added in #164. The nightly `mutation` job had no browser, so those
four failed and Stryker aborted with "There were failed tests in the initial test run" before
mutating anything. **The same latent failure sits in CI's `fast` lane**, which runs
`pnpm test:coverage` over the same files with no browser either — it has simply never been
reached, because `pnpm security:audit` fails earlier in that job and short-circuits it. Clearing
B-01 would have exposed it immediately. Fixed by adding the existing cached
`./.github/actions/playwright` (project `chromium`) to both jobs; `playwright install chromium`
provides both `chromium` and `chromium_headless_shell` (verified with `--dry-run`).

**D-02 — `pnpm build` was broken on `main`, undetected locally.**
`lib/notifications/print-kit-browser.ts` (added in #164) imports `playwright`, but only
`@playwright/test` was declared; under pnpm's strict layout `playwright` is not linked at the
project root. CI run 30195146721 on `20b48b7a` fails `Production build` with
`Cannot find module 'playwright'`, and has since #164 landed. It was masked locally because
`require.resolve("playwright")` resolved to a stray copy in the developer's **home directory**
(`~/node_modules/playwright`), outside the repository — so local "green" builds were not
trustworthy. Fixed by declaring `playwright@^1.61.1` (already in the lockfile via
`@playwright/test`, so no new resolved package). Dev-only: the import chain is reachable solely
from CLI export scripts and unit tests, never from `app/` or `components/`.
