## 2. Injection surfaces

### 2.1 `pull_request_target` — exactly one, and it is safe by construction

`.github/workflows/factory-status.yml:8-9`: `pull_request_target: [opened, synchronize, reopened, ready_for_review]` (also `workflow_run` :5-7, `schedule` :10-11, `workflow_dispatch` :4).

Why the classic `pull_request_target` dangers do not apply here:

- **It never checks out the PR.** The job checks out `ref: main` with `persist-credentials: false` (`.github/workflows/factory-status.yml:30-33`) and its comment (:23-25) states "Never check out the triggering PR/run, execute candidate code, install dependencies or download candidate artifacts."
- **No secrets.** The only credential is `GH_TOKEN: ${{ github.token }}` (:39), scoped by the all-read `permissions:` block (:13-17).
- **The executed code is reviewed main code.** `node scripts/ci/factory-status.mjs --summary` (main tree) is read-only: it reads commits/pulls/releases via the GitHub API (`scripts/ci/factory-status.mjs:36-45`, imports at :6-16); a grep over the script finds no POST/create/update calls.
- Residual risk is maintainer trust in main's copy of `factory-status.mjs` — the same trust as any workflow file — not fork-PR code execution. A fork PR merely triggers a metadata-only, read-only report run (concurrency group `delivery-decision-report` with `cancel-in-progress` :19-21 bounds run-spam).
- Verdict: the two canonical anti-patterns (`pull_request_target` + PR-head checkout; `pull_request_target` + secrets) are both absent. This is the correct way to use the trigger if it is needed for PR-context reporting.

### 2.2 `workflow_run` consumers and PR-controlled data

- `production-database.yml:4-7`: on `CI` completed, **`branches: [main]` filter** — a fork PR's CI run (event `pull_request`, head repo ≠ this repo) cannot satisfy the filter. The `preflight` job then hard-binds the promotion to trusted sources (`.github/workflows/production-database.yml:38-76`): `workflow_run.conclusion == success`, `GITHUB_REF == refs/heads/main`, `EXPECTED_REVISION == GITHUB_SHA`, dispatch confirmation string, and — for the workflow_run path — `production-deploy.yml:51-73` re-verifies caller run id/attempt (`gh api repos/.../actions/runs/$GITHUB_RUN_ID` path must be `.github/workflows/production-database.yml`), `[[ "$EXPECTED_REVISION" =~ ^[a-f0-9]{40}$ ]]` (:56), the source run's workflow path must be `ci.yml` (:64-65), `SOURCE_EVENT == push`, `SOURCE_REPOSITORY == GITHUB_REPOSITORY`, `SOURCE_BRANCH == main`, `SOURCE_REVISION == EXPECTED_REVISION` (:59-67). All `workflow_run.head_sha`-derived values enter shell via `env:` indirection (`.github/workflows/production-database.yml:33, :87, :236, :287, :346`), never direct interpolation.
- `production-smoke.yml:6-8`: on `Production database promotion` completed; the job-level guard requires `conclusion == 'success' && head_branch == 'main'` (`.github/workflows/production-smoke.yml:29`), checkout ref via env-guarded `with:` (:42), run ids via `env:` (:46-58).
- `factory-status.yml:5-7`: `workflow_run` on CI/CodeQL/database-promotion with no branch filter, but the job is the same read-only, main-pinned report as above.
- `production-deploy.yml:5`: `workflow_call` only (plus the caller's preflight binding above). `CONFIRMATION`, `SOURCE_*` values all enter via `env:` (`.github/workflows/production-deploy.yml:38-49`) and are consumed as quoted shell variables with regex/identity assertions (:51-73).

### 2.3 `${{ github.* }}` inside `run:` blocks

Exhaustive grep over `.github/workflows/` and `.github/actions/`:

- **Zero** `${{ github.* }}` expressions inside any `run:` block (single-line or heredoc). Every PR-influenced value (`pull_request.base.sha`, `head.sha`, `head.repo.full_name`, `workflow_run.*`, `github.token`) enters through `env:` or action `with:` parameters and is consumed as a quoted shell variable — the env-indirection safe pattern. Representative citations: `.github/workflows/ci.yml:39-41` (CI_BASE_SHA/CI_HEAD_SHA/CI_HEAD_REPOSITORY) consumed at :76 and :92 as `"$CI_BASE_SHA"`; `.github/workflows/ci.yml:235` REVIEWED_REVISION env → `:237-243` shell assertions; `production-smoke.yml:49-58`; `production-database.yml:33-36`.
- Direct single-line `run:` interpolation exists only for **static, workflow-defined matrix values** — not attacker-controllable:
  - `.github/workflows/ci.yml:482` (`${{ matrix.project }}`, `${{ matrix.pack }}`), `:533`, `:651`; `.github/workflows/nightly.yml:94`. Matrix lists are literals in the same files (`ci.yml:456-464`, `:514-521`, `:568-572`, `:631-640`).
  - `.github/actions/playwright/action.yml:39,44` interpolate `steps.resolve.outputs.browser`, which is produced by the static `case` at :19-23 from `inputs.project`; every caller passes a static literal or a static matrix value (`ci.yml:190-197, :582-584`; `nightly.yml:92-93`; `production-database.yml:181-185`).
- **One genuine deviation from the env-indirection rule:** `.github/workflows/recovery-drill.yml:41` — `[[ "${{ inputs.backup_id }}" =~ ^[0-9]+$ ]]` interpolates a `workflow_dispatch` input directly into a `run:` block, while its sibling inputs use `env:` (:33-35). Dispatch requires repo write access, so the only injector is an already-authorized operator (self-infliction at worst), but the same line proves its own point: the regex check should run against an env variable. Low severity; fix is mechanical.
- No `secrets: inherit` anywhere (`grep -rn "secrets: inherit" .github/` → none): the called `production-deploy.yml` receives exactly five named secrets from the caller (`.github/workflows/production-database.yml:446-451`).

### 2.4 Fork PRs — no elevated context

Fork PRs receive: read-only CI/CodeQL/dependency-review runs (no secrets — §6.1), a read-only `factory-status` report (§2.1), and are **refused** by the local-CI bridge (`.github/workflows/local-ci-shadow.yml:22-33`: the job runs only when `github.event.pull_request.head.repo.full_name == github.repository` or a push to main; comment :18-21 spells out the fork-PR rationale). The ruleset requires PR + status checks to merge. No `pull_request_target` job exposes secrets or a write scope (§2.1).
