# Nabaperks Merchant `/app` Code Review

**Scope:** All authenticated merchant routes behind `app/app/layout.tsx` (auth gate + `MerchantAppShell`).
**Method:** Source-grounded, file:line-cited, adversarially verified. Severities reflect the verdicts after verification (several findings were downgraded from their original ratings once the consuming code or DB backstops were inspected).

---

## 1. Executive Summary

**Overall health: solid and security-sound, with a long tail of polish.** The single most important result is what the review did **not** find: there are **no exploitable IDOR or PII-leak vulnerabilities** on any route. Every data loader is scoped to the authenticated merchant resolved from the session (`getCurrentMerchant()` → `owner_user_id = auth.uid()`), tenant ids are never read from `params`/`searchParams`/`body`, the `[rewardId]` scan RPC (`get_reward_scan_context`) enforces ownership in SQL (`token_merchant_id <> p_merchant_id → 'unauthorized'`), `/app/customers` masks all PII server-side before the client boundary, and the one `notFound()`/redirect path that hand-builds a `next=` URL is neutralized by downstream sanitizers. **0 critical, 0 high** after verification.

The findings cluster into **15 medium** and a large body of **low/info** items dominated by four recurring themes:

1. **Redundant, uncached data-fetching across the dashboard and launch surfaces.** The same rows are fetched 2–4× per render because parallel loader stacks (`getQrSetupFresh`, `getLoyaltyCardSetup`, `getMerchantBilling`, `getMerchantCustomers`, the merchants row) don't share results, and `getQrSetupFresh` deliberately bypasses the `cache()`-wrapped variant. Individually small (single-row, indexed, often parallelized), collectively a clear efficiency drag.
2. **The dashboard over-fetches the full 100-row customer list (4 queries + 100 readback view-models + PII) purely to derive two integers** (`readyCount`/`quietCount`). This is the single largest avoidable cost on `/app` and recurs verbatim on every dashboard load. (3 routes flagged the same line — merged below.)
3. **Accessibility gaps on form/interaction feedback.** Server-action results (success/error) are injected with no `aria-live` region across onboarding, profile, and the scanner error path; the desktop customers table row is mouse-only (WCAG 2.1.1 keyboard failure); heading hierarchies skip levels or vanish on mobile.
4. **One genuine WCAG AA contrast failure:** the `StatStrip` "sun"/amber metric renders at **1.91:1** in light mode (QR count on `/app/activity`, "Quiet" count on `/app/customers`) — below even the 3:1 large-text floor.

**The 4 highest-value fixes:**
- **Stop loading `getMerchantCustomers` on the dashboard** — replace with two `head:true` counts or fold into `get_merchant_dashboard_metrics`. Removes 3–4 queries + a 100-row PII transfer + ~100 `Intl` allocations from the hottest authed page.
- **Fix the `StatStrip` "sun" tone** — map amber to an ink-on-fill chip or a darker AA-safe token; it's a real AA failure on two screens.
- **Defer/redo the launch transient-param cleanup** — the `router.replace` on mount can blank a just-shown success banner (and its Continue CTA) before it can be read.
- **Push `filter`/`q` into the activity DB query** — deep-linked `?filter=reward` currently filters only the already-loaded window, producing false "No events" states and O(history) paging.

## 3. Findings by Route

### `/app` — Merchant dashboard home

**What it does:** `app/app/layout.tsx` auth-gates via `getCurrentUser()` (React-cached `auth.getUser` on the SSR cookie client) and redirects anon users to merchant login; otherwise renders `MerchantAppShell`. `app/app/page.tsx` awaits `getMerchantOnboardingStatus()` (re-resolves the user, selects `merchants WHERE owner_user_id = user.id`, counts locations; redirects to `/app/onboarding` unless complete), then streams `MerchantDashboardStream` inside Suspense. The stream `Promise.all`s four heavy loaders (dashboard metrics, launch readiness, 14-day series, customers) and a compact-activity island. `setup.merchant.id` is the only tenant key threaded downstream — never from the URL.

#### Medium
*(none unique to this route — the dashboard over-fetch verified here is consolidated under `/app/customers` Medium since it shares the exact line.)*

#### Low / Info
- **Serial await in `getMerchantDashboardData`** — *low, perf* — `lib/merchant/dashboard-metrics.ts:18-21`. The metrics RPC is awaited, then `loadMerchantDashboardTrends` (itself 8 parallel COUNTs at `:395-404`) is awaited strictly after, despite being data-independent. Verified the caller already wraps this in a 4-way `Promise.all`, so it does **not** "double the tile critical path" — the realized saving is one extra round-trip on one of four parallel arms behind Suspense. **Fix:** `const [base, trends] = await Promise.all([getMerchantDashboardMetrics(merchant).then(r => r ?? getMerchantDashboardDataByQuery(merchant)), loadMerchantDashboardTrends(merchant.id)]); return { ...base, trends }`.
- **`billing_customers` row read twice per render** — *low, perf* — `lib/merchant/billing.ts:27`. `getMerchantDashboardData` (RPC `billing_status` or fallback `getBillingStatus`) and `getMerchantLaunchReadiness` → `getMerchantBilling` both read the same single row; they run as `Promise.all` siblings so ~zero wall-clock cost. **Fix:** thread the resolved billing status into launch readiness, or `cache()`-wrap `getMerchantBilling`.
- **`merchants` row re-queried because onboarding bypasses cached `getCurrentMerchant`** — *low, perf* — `lib/merchant/onboarding.ts:44`. `getMerchantOnboardingStatus` runs its own `merchants` select; `getQrSetup → getCurrentMerchant` runs a second near-identical one (and `getMerchantRequiresBilling` a third, service-role, by id). All correctly tenant-scoped — efficiency only. **Fix:** resolve the merchant via the `cache()`-wrapped `getCurrentMerchant` in onboarding, extending its select list.
- **`getMerchantDashboardSeries` re-counts total members** — *low, perf* — `lib/merchant/dashboard-metrics.ts:72`. A 4th COUNT of `customer_memberships` to back-compute the members-sparkline baseline duplicates `metrics.members`. **Fix:** `getMerchantDashboardSeries(merchant.id, { totalMembers: metrics.members })` and drop the count.
- **14-day series buckets by UTC day; customer badges use Europe/London** — *low, correctness* — `lib/merchant/dashboard-metrics.ts:104`. During BST, a 00:30 event plots on yesterday's bar but shows "New today" — cross-component disagreement around UK midnight. **Fix:** bucket the series by `Europe/London` calendar day using the existing `londonDateKey` helper; keep the `.gte()` filter on a UTC instant derived from London midnight.
- **Members sparkline baseline omits true starting count and ignores churn** — *low, correctness* — `lib/merchant/dashboard-metrics.ts:87`. `members[i] = baseline + Σjoins`, where `baseline = totalMembers − joinsInWindow`; the baseline point is never plotted and deletions break the assumption, yet the JSDoc claims an exact count. **Fix:** compute the true pre-window count (`count where created_at < sinceIso`) and prepend it, or soften the comment to "estimate".
- **`TrendChart.project` derives x-step from unfiltered length but plots only finite points** — *low, correctness* — `components/data/trend-chart.tsx:31`. Any NaN/Infinity would misalign the line/fill from the x-axis; latent today (series are always finite ints) but diverges from the safe `Sparkline.buildPoints`. **Fix:** filter first, then `step = VIEW_W / Math.max(1, clean.length - 1)`.
- **Launch-readiness serializes billing behind multi-round-trip `getQrSetup`** — *low, perf* — `lib/merchant/launch-readiness.ts:215`. Billing only needs `merchant.id` (already available) but is awaited after the 3-deep QR chain. **Fix:** `Promise.all([getQrSetup(), getLaunchBillingReadiness(merchant.id)])`.
- **Empty-state renders a second `<h2>` in the activity card** — *low, ux* — `components/merchant/dashboard-home-streams.tsx:273`. `MerchantCompactActivityStream`'s `EmptyState` defaults to `headingLevel=2`, peering with the card's "Recent activity" h2 on the default first-run path. **Fix:** `<EmptyState ... headingLevel={3} />`.
- **Error boundary starts heading outline at h2 (no h1)** — *low, ux* — `app/app/error.tsx:18`. The page's only h1 (`PageTitle`) unmounts; `error.tsx`'s `EmptyState` becomes the first heading at level 2. **Fix:** `<EmptyState ... headingLevel={1} />`.
- **`/app` omits `export const dynamic = "force-dynamic"`** — *info, perf* — `app/app/page.tsx:24`. Dynamic only as a side effect of cookie access; siblings `/app/launch` and `/app/account` declare it explicitly. **Fix:** add `export const dynamic = "force-dynamic"` for defense-in-depth.
- **Overlapping `role="status"` live regions during streaming** — *info, ux* — `components/merchant/loading-skeletons.tsx:43`. Route-level + two sibling Suspense fallbacks each announce, producing redundant "Loading…" announcements. **Fix:** keep one authoritative region; `aria-hidden` the inner skeletons or drop `role="status"` from one.

### `/app/launch` — Guided setup (venue / card / rewards / QR / billing tabs)

**What it does:** Auth-gated; `MerchantAppShell` variant `setup`. `force-dynamic` page awaits `searchParams`, resolves `getCurrentMerchant()` (→ `/app/onboarding` if null), then `getQrSetupFresh()` + `getLaunchBillingReadiness()` (service-role) → `buildLaunchReadiness()`. A **provision gate** writes a join QR on render when venue+card+rewards are ready but no QR exists. The active tab's panel renders inside a `key={activeTab}` Suspense boundary; each panel re-fetches its own data.

#### Medium
- **Client transient-query cleanup races and can blank a just-shown success banner** — *medium, correctness/ux* — `app/app/launch/page.tsx:138` + `components/merchant/launch/launch-tab-auto-advance.tsx:18`. On mount, `LaunchTransientQueryCleanup` fires `router.replace(cleanHref)` with no delay, stripping `saved/seeded/created/enabled/qr`. Because the page is `force-dynamic` and the success banners (`CardStatus` on `saved==='1'`, `RewardsStatus` on `saved==='pool'`, QR `statusMessage`) are server-rendered from those params, the RSC re-renders without them and the banner — plus its inline "Continue to the next step" CTA — can vanish near-instantly on a fast client. (Two route reviews flagged this; merged.) **Fix:** use `history.replaceState` (no RSC refetch) instead of `router.replace`, or defer the scrub behind a timeout/interaction, or drive the banner from client state captured on first mount. *Note: `disabled=1` is not in the strip list, so that one banner is preserved (see related Low).*
- **QR tab re-runs the entire data pipeline (uncached) — ~double the round-trips** — *medium, perf* — `components/merchant/launch/qr-panel.tsx:41`. The page body builds readiness with `getQrSetupFresh()` + `getLaunchBillingReadiness()`; `QrPanel` then runs the identical pipeline again. `getQrSetupFresh` deliberately wraps `getQrSetupUncached` (not the `cache()`-wrapped `getQrSetup`), so nothing dedupes: ~6 sequential round-trips + 4 service-role reads where one render's worth would do, and in steady state `QrPanel`'s recomputed readiness is discarded. **Fix:** compute readiness once in the page and pass resolved data to `QrPanel` as props; run the provision side-effect in exactly one place. If a panel fetch must stay, route it through the `cache()`-wrapped `getQrSetup`.
- **`LaunchPanelSkeleton` doesn't mirror the card/rewards layouts → CLS on every tab switch** — *medium, ux* — `components/merchant/loading-skeletons.tsx:314`. The fallback is a single-column 4-field stack with `p-6` for *all* tabs, but `card` is a 2-column `lg:grid-cols-[minmax(0,1fr)_320px]` with a preview panel and `p-3 sm:p-6`, and `rewards` is a counter header + variable reward rows + dashed add-button. `key={activeTab}` re-mounts the boundary on every switch, so the jump recurs. The skeleton's own comment promises "never shifts the layout". **Fix:** branch the skeleton by tab (2-col shell for `card`, header+rows for `rewards`, simple stack for `venue`); at minimum align padding to `p-3 sm:p-6`.

#### Low / Info
- **Partial default-reward seed leaves merchant below 3 rewards with no error** — *low, correctness* — `lib/merchant/seed-default-reward-pool.ts:25`. Each `upsert_reward_pool_item` is its own transaction; a mid-loop failure commits 1–2 of 3, then the re-seed gate (`length === 0`) never re-fires. Self-heals via the always-rendered "Add a reward" form + live `1 / 3 active` counter, and is low-probability, but non-atomic. **Fix:** a single transactional bulk-seed RPC, or surface a recoverable `?error=seed_failed`, or gate re-seed on active-count `< 3`.
- **`QrPanel` duplicates the provision + readiness pipeline** — *low, correctness* — `components/merchant/launch/qr-panel.tsx:40`. Same root as the Medium perf finding; correctness angle is duplicated logic that can drift. Verified the two provision attempts are **sequential** (RSC parent resolves before child), so no concurrent `create_or_get_join_qr` — the RPC is idempotent regardless. **Fix:** provision/load once at page level; drop the panel's second gate.
- **Mutations run during `force-dynamic` GET render with errors swallowed** — *low, correctness* — `app/app/launch/page.tsx:94`. `ensureJoinQrProvisioned` issues `create_or_get_join_qr`/`set_qr_active` on render and returns `{provisioned:false}` on *any* RPC error (`ensure-join-qr.ts:42-44, 64-66`), indistinguishable from "not eligible". Reachable only by an authenticated, nearly-onboarded merchant's own GET (layout + merchant gates block crawlers). **Fix:** move writes to the existing server actions/POST, or at minimum log the error and surface `?tab=qr&error=...`.
- **Reward-pool count fetched twice (`getQrSetup` + `getLoyaltyCardSetup`)** — *low, perf* — `lib/merchant/loyalty-card.ts:85`. Both stacks re-load location + card + reward pool independently per render. **Fix:** a single `cache()`-wrapped "setup snapshot" loader feeding both; at minimum `cache()` the location lookup.
- **Five panels wrapped in one Suspense but data is fetched eagerly first** — *low, perf* — `app/app/launch/page.tsx:74`. The shell above the boundary depends on the eagerly-awaited pipeline, so no early shell streams; the skeleton only covers the panel's own (duplicate) fetch. **Fix:** move readiness/provision fetching into the suspended subtree, or drop the Suspense pretense and `Promise.all` at the top.
- **Page-level loaders run as a serial waterfall** — *low, perf* — `app/app/launch/page.tsx:74`. Billing keys off the session merchant (already resolved) but is awaited after `getQrSetupFresh`. **Fix:** `const [setup, billing] = await Promise.all([getQrSetupFresh(), getLaunchBillingReadiness(merchant.id)])`.
- **`force-dynamic` + uncached loaders re-query Supabase on every navigation** — *low, perf* — `app/app/launch/page.tsx:33`. No request-spanning cache; mixed posture (`getLoyaltyCardSetup`/`getCurrentMerchant` cached, `getQrSetupFresh` not) is a maintenance hazard. **Fix:** `revalidatePath('/app/launch')` in mutating actions and use the `cache()`-wrapped `getQrSetup` for reads.
- **`transientCleanHref` omits `disabled` → stale "QR code disabled" banner** — *low, correctness* — `app/app/launch/page.tsx:139`. `setQrActiveAction` redirects to `?tab=qr&disabled=1` and `statusMessage` treats `disabled` as transient, but the cleanup condition omits it. **Fix:** add `params.disabled` to the condition.
- **Billing readiness uses a permissive 2-state denylist** — *low, correctness* — `lib/merchant/launch-readiness.ts:175`. "Any status except cancelled/suspended" treats `past_due`/`unpaid`/`incomplete` as launch-ready, disagreeing with `BillingPanel`'s finer model. **Fix:** switch to an allowlist (`active`, `trialing`, …) or reuse `BillingPanel`'s predicate.
- **`getMerchantRequiresBilling` fails open silently on transient error** — *low, correctness* — `lib/merchant/launch-readiness.ts:253`. Returns `true` on any Supabase error (direction is safe — gates rather than opens) but can flip readiness on a blip with no signal. **Fix:** log the error and distinguish "unknown due to error" from a real `requires_billing=true`.
- **Scan/collect RPCs trust caller-supplied `p_merchant_id` (defense-in-depth)** — *low, security* — `supabase/migrations/20260626090000_require_merchant_billing.sql:243`. **Not exploitable today** — both callers pass session-derived `merchant.id`. Risk is forward-looking: `SECURITY DEFINER` + service-role means a future caller forwarding a request-supplied id would gain cross-tenant access. **Fix:** add a self-contained ownership assertion (`is_service_role_request()` OR `exists(... owner_user_id = auth.uid())`), matching `create_or_get_join_qr`.
- **Mobile heading hierarchy broken/inconsistent — card/rewards/billing have no h1** — *low, ux* — `app/app/launch/page.tsx:145`. The page h1 is `hidden sm:grid`; on mobile, `venue`/`qr` tabs supply an h1 (their panels' `PageTitle`) but `card`/`rewards`/`billing` start at h2 — heading level changes live across tabs. (Not a hard WCAG SC failure — the h2s are real and descriptive — but a best-practice/consistency gap on a mobile-first first-run surface.) **Fix:** one stable always-present h1 (render `PageTitle` at all breakpoints or an `sr-only` mobile h1) and demote per-panel h1s to h2.
- **Protected QR `<img>` has no intrinsic dimensions / matching skeleton** — *low, ux* — `components/merchant/launch/qr-panel.tsx:170`. Cookie-protected images load over the network; aspect wrappers absorb most shift but the status line and preview thumbs still flash. **Fix:** add explicit `width`/`height`, a `bg-secondary` placeholder, and a status-line bar in the qr skeleton.
- **Loaders surface raw Supabase `error.message` in thrown errors** — *info, security* — `lib/merchant/reward-collection.ts:44`. Not user-visible (`error.tsx` is generic; Next redacts to a digest in prod), but raw DB hints land in logs. **Fix:** log raw server-side, throw a stable non-revealing message.

### `/app/onboarding` — First-run merchant setup form

**What it does:** Auth-gated. `page.tsx` awaits `getCurrentUser()` + `getMerchantOnboardingStatus()` (selects `merchants WHERE owner_user_id = user.id`, counts locations → `needs_profile | missing_location | complete`; redirects to `/app/launch` if complete). Otherwise renders the client `OnboardingForm` with `initialFields`, `draftUserId`, and the public Google Maps key. Submit calls `completeOnboardingAction` (server) which re-checks the user and creates the merchant + primary location via `create_merchant_onboarding`.

#### Medium
- **Validation errors are not announced to SR and focus never moves to the first error** — *medium, ux* — `components/merchant/onboarding-form.tsx:285`. `completeOnboardingAction` returns errors via `useActionState` with no navigation; the form-level error is injected into a plain `<p>` with no live region and no focus move. A keyboard/SR user pressing "Finish setup" on a failed submit gets silence, focus stuck on the button. **Hard failure is WCAG 4.1.3** (status messages); per-field errors *are* wired with `aria-invalid`/`aria-describedby`, so 3.3.1 is satisfied once a field is reached. **Fix:** wrap the form-level error in `role="alert"`; in the existing `useEffect([state.fields])`, focus the first `[aria-invalid="true"]` field. *(The same non-live `<p>` pattern recurs in `customer-login-form`, `loyalty-card-form`, and the profile form — fix the shared pattern.)*

#### Low / Info
- **Dead venue-name "required" validation — blank name silently persisted as "Main venue"** — *low, correctness* — `lib/merchant/venue-location-submission.ts:62`. `value(formData, venueNameField) || "Main venue"` defaults before validation, so the `!submission.venueName` guard at `:98-99` is unreachable in *every* caller; the form wires an error slot (`state.errors.locationName`) that can never populate. Benign placeholder, fully editable later. **Fix:** preserve the raw value at parse time and apply "Main venue" only post-validation (or behind an explicit `{ defaultVenueName }` option) so the guard fires.
- **`getMerchantDashboardData` serial await** — *low, perf* — `lib/merchant/dashboard-metrics.ts:21`. *Duplicate of the `/app` finding; mis-routed here (this page never imports the loader).* See `/app`.
- **Required fields not marked `required`/`aria-required`** — *low, ux* — `components/merchant/onboarding-form.tsx:190`. Server treats business name/type, location name, and address line1/city/postcode as required, but markup advertises every input as optional (no `*`, no `aria-required`) — WCAG 3.3.2 (Level A) affordance gap. **Fix:** plumb a `required` prop through `Field`/`businessType`/`AddressField` and add a visible `*` + `sr-only "required"`.
- **Missing `autocomplete` tokens on phone/address** — *low, ux* — `components/merchant/onboarding-form.tsx:277`. `tel` field and address lines lack tokens (postcode correctly uses `postal-code`), hurting autofill on a mobile-first form. (Strict WCAG 1.3.5 applies cleanly only to the phone field — venue address/name aren't *user* data.) **Fix:** `autoComplete="tel"`, `address-line1/2`, `address-level2`.
- **`user!.id` dereferenced without a local null guard** — *low, correctness* — `app/app/onboarding/page.tsx:34`. Relies entirely on the layout guard; `getCurrentUser` is request-cached so safe today, but a layout refactor would throw a 500 instead of redirecting. **Fix:** `if (!user) redirect(merchantLoginHref("/app/onboarding"))` before the status check.
- **Redundant total-member COUNT** — *low, perf* — `lib/merchant/dashboard.ts:72`. *Duplicate of the `/app` series-count finding.*
- **`reward_events` redeemed history fetched unbounded to take the latest per membership** — *low, perf* — `lib/merchant/dashboard.ts:99`. Pulls every redeemed row for ≤100 memberships, keeps only the most recent each. Bounded by redemption volume, grows with usage. **Fix:** `DISTINCT ON (membership_id) ... ORDER BY redeemed_at DESC` view/RPC, or cap to a 90-day window.
- **Submit button has no `aria-busy` while pending** — *low, ux* — `components/merchant/onboarding-form.tsx:290`. Sighted users see "Saving…"; SR users get nothing (WCAG 4.1.3). **Fix:** `aria-busy={pending}` on the button/form.
- **No own `loading.tsx`/`error.tsx`; shared error copy is dashboard-specific** — *low, ux* — `app/app/onboarding/page.tsx:18`. Shared fallbacks reference dashboard concepts a brand-new merchant lacks. **Fix:** optional `app/app/onboarding/error.tsx` with setup-appropriate copy.
- **Google Places input not associated with its visible "Find your venue" label** — *low, ux* — `components/merchant/launch/venue-place-autocomplete.tsx:270`. SR announces only the placeholder. **Fix:** give the span an `id` and set `aria-labelledby` on the injected element.
- **`persistVenueLocationWrite` relies solely on RLS + RPC-provenance (latent IDOR if reused)** — *info, security* — `lib/merchant/venue-location-submission.ts:181`. **Safe today:** `locationId` comes from the `SECURITY DEFINER` RPC, the write uses the cookie-bound anon/RLS client, and the `merchant_locations` UPDATE policy enforces `is_merchant_owner` in `using`+`with check`. Verified the whole route clean (no open redirect, public Maps key only, scan RPCs reject cross-merchant). **Fix:** add `.eq("merchant_id", payload.merchant_id)` to the update for self-defending defense-in-depth.

### `/app/customers` — Loyalty members table (PII surface)

**What it does:** Auth-gated → `getCurrentMerchant()` (null → `/app/onboarding`) → reads `searchParams.highlight` (reduced to one string) → Suspense-wraps `CustomersTableStream(merchant.id, highlightedMembershipId)`. The stream awaits `getMerchantCustomers(merchantId)` (**service-role** client, RLS-bypassed; `customer_memberships .eq('merchant_id', …) limit 100` + 3 parallel reward/card queries) which returns rows **still containing raw email/phone**, then maps every row through `buildMerchantCustomerReadback` **before** the client boundary, so only masked view-models reach `CustomerReadbackTable`.

#### Medium
- **PII masking is enforced by one `.map()`, not the type system** — *medium, security* — `app/app/customers/page.tsx:67`. **Safe as written** — the client component is typed `MerchantCustomerReadbackRow[]` (no raw PII field) and the page masks every row first. But `MerchantCustomerRow` is a plain structural type sharing `id`/stamp fields with the client's needs, with **no brand, no DB backstop on this path** (service-role bypasses RLS), and **no test coverage** (checked-in tree has no unit tests). A future refactor spreading a raw row into a client component would compile and silently ship every member's email + phone. The identical un-walled pattern is **duplicated at `dashboard-home-streams.tsx:60-62`**. **Fix:** make the mask un-bypassable — brand `MerchantCustomerRow` with a unique symbol, or have `getMerchantCustomers` return the already-masked shape so raw PII never escapes `lib/merchant/*`.
- **Dashboard over-fetches the full 100-row customer list (4 queries) just to derive two integers** — *medium, perf* — `components/merchant/dashboard-home-streams.tsx:52`. **Consolidated finding (flagged on `/app`, `/app/customers`, and `/app/scan`).** `getMerchantCustomers` runs 4 DB round-trips + builds ≤100 `buildMerchantCustomerReadback` view-models (each allocating several `Intl.DateTimeFormat`) + pulls raw email/phone, solely to compute `readyCount`/`quietCount` for the "Do next" card — the home page never renders the table. Verified: the array's *only* consumers are the two `.filter().length` calls (`:60-64`); PII never reaches the client (server-side only); the badge precedence (first-match-wins) means a naive `last_visit ≥ 30d` count would over-count "quiet", so the replacement needs care. It is the single largest avoidable loader on `/app`, runs every render, and scales with member count. **Fix:** replace with two `head:true` counts (`reward_events status='unlocked' AND redeemable_from<=now`; `customer_memberships last_visit_at < now-30d`, respecting badge precedence) or extend `get_merchant_dashboard_metrics` to return `rewards_ready`/`gone_quiet`. Drop `getMerchantCustomers` from the dashboard `Promise.all`.
- **Desktop table rows are click-only — selection + reward-scan unreachable by keyboard** — *medium, ux* — `components/merchant/customer-readback-table.tsx:417`. `onRowClick` wires `onClick` onto a bare `<tr>` (`DataTableCore` → `ui/table.tsx` adds no `tabIndex`/`role`/`onKeyDown`); cells contain only non-interactive elements. Read → `notFound()`; collect raises `'Reward scan token expired'`, which matches `merchantCollectionBlockedCopy` only because Postgres-prefixed message *contains* the `'scan token expired'` needle (no data-integrity bug — the DB still refuses). **Fix:** add an explicit `expired` `scan_status` branch, or key the copy match on a stable token like `'expired'`.
- **`redeemed` banner can render with empty reward name / blank customer label** — *low, correctness* — `lib/merchant/reward-collection.ts:161`. The loader coalesces missing fields to `""`/"Customer" while the TS union declares them always-present — a false guarantee if the RPC ever returns a partially-populated redeemed row. **Fix:** return `{status:'not_found'}` when a promised-non-optional field is missing, or type them `string | null` and guard the render sites.
- **Login redirect built without the sanitizer/`encodeURIComponent`** — *low, correctness + low, security* (two reviews; merged) — `app/app/rewards/scan/[rewardId]/page.tsx:49`. **Not an exploitable open redirect** — `[rewardId]` is a single segment (can't hold `//host`), and both `next` consumers sanitize at the sink (`safeMerchantNextPath`; the magic-link route strips to same-origin). Residual: an exotic param with `?`/`#` could inject stray chars, and it diverges from the shared sanitizer. **Fix:** `redirect(merchantLoginHref("/app/rewards/scan/" + encodeURIComponent(scanToken)))`.
- **Loader return over-fetches raw email/phone beyond what's rendered (latent PII)** — *low, security* — `lib/merchant/reward-collection.ts:166`. **No leak today** — only the masked `customerLabel` is in the return type, the page renders only that + `membershipId.slice(0,8)`, the client form gets only the token string, and no logging exists. The RPC returns raw PII into TS, so masking is hand-maintained discipline. **Fix:** never add raw email/phone to `MerchantRewardScanContext`; ideally have the RPC return only a server-computed masked label + `phone_last4`.
- **Heading hierarchy skips h1 → h3** — *low, ux* — `app/app/rewards/scan/[rewardId]/page.tsx:70`. `PageTitle` is h1; `RewardTicket` renders the reward name as h3 with no h2 between (StatusBanner uses a `<div>`, not a heading) — WCAG 1.3.1/2.4.6. **Fix:** add an (sr-only) `<h2>` before `RewardTicket`, or give `RewardTicket` a `headingLevel` prop.
- **"Collected" confirmation driven purely by `?collected=1`, not server state** — *low, ux* — `app/app/rewards/scan/[rewardId]/page.tsx:72`. The success ticket + banner can be shown from the URL alone (bookmark/bfcache replay) even when `scan_status` is still `ready` (the destructive mutation is still server-guarded). **Fix:** gate the success banner on `context.status === 'redeemed'`; let the param only upgrade copy.
- **Customer/card readout uses span pairs rather than a description list** — *low, ux* — `app/app/rewards/scan/[rewardId]/page.tsx:78`. Label↔value association isn't exposed to AT (four disconnected strings). **Fix:** render as `<dl>`/`<dt>`/`<dd>` (styling unchanged).
- **Dead defensive guard `if (!('rewardId' in context))`** — *info, correctness* — `app/app/rewards/scan/[rewardId]/page.tsx:64`. Statically unreachable after the switch narrows the union; harmless but gives a false sense of a runtime check. **Fix:** remove it, or convert to an exhaustive `switch` with a `never` default.

## 4. Cross-Cutting Recommendations

### Auth & merchant-scoping (the model holds — keep it that way)
- **No exploitable IDOR or PII leak exists.** Every loader scopes to the session-resolved `merchant.id`; the URL never feeds a tenant id. Preserve this invariant.
- **Harden the service-role paths with defense-in-depth.** `getMerchantCustomers`, `getMerchantBilling`, and the scan/collect RPCs all bypass RLS and rely 100% on caller discipline. Add self-defending guards: prefer the anon/RLS client where possible (mirror `profile.ts`), add explicit `.eq("merchant_id", …)` predicates, and add in-RPC ownership assertions (`is_service_role_request()` OR `owner_user_id = auth.uid()`), matching the safer `create_or_get_join_qr`/`set_qr_active` pattern.
- **Make PII masking structural, not procedural.** The `/app/customers` mask (and its duplicate on the dashboard) is one `.map()` away from regression. Brand `MerchantCustomerRow` or have loaders return the masked shape so raw PII can't escape `lib/merchant/*`. Switch `activity.searchText` from a name-substring denylist to an explicit allowlist.
- **Declare `force-dynamic` explicitly on all PII/per-merchant pages** (`/app`, `/app/customers`, `/app/activity`, the scan route) so no-cache is a contract, not an emergent side effect of cookie access.

### Data-fetching & performance
- **Stop the dashboard customer over-fetch** (the #1 perf win): replace `getMerchantCustomers` on `/app` with two `head:true` counts or RPC fields.
- **Eliminate redundant reads via shared caching.** `getQrSetupFresh` defeats request memoization by bypassing the `cache()` wrapper; the merchants/billing/reward-pool/location rows are each fetched 2–3× per render across parallel stacks. Introduce a single `cache()`-wrapped "setup snapshot" loader and route `getMerchantBilling`/`getMerchantRequiresBilling` through `cache()`.
- **Parallelize independent awaits** (`getMerchantDashboardData` metrics+trends; launch page setup+billing) — trivial `Promise.all` wins.
- **Move writes out of GET render** on `/app/launch` (provision/seed) into server actions/POST, and stop swallowing RPC errors.
- **Adopt keyset pagination + `limit+1` sentinels** on `/app/activity` to drop the per-page exact count, the offset-style re-fetch, and the dead `details[]` payload.

### Design system (Wet Ink)
- **Fix the one real AA failure:** `StatStrip` "sun"/amber as foreground text is 1.91:1 in light mode (QR on activity, Quiet on customers). Map it to an ink-on-sun chip or a darker AA-safe token; amber is a *fill*, not a text color, per DESIGN.md. The "Stamp" tinted badge at ~4.44:1 should also clear 4.5:1.
- **Make skeletons mirror their surfaces** (the system's stated contract): launch panel skeleton by tab, customers table columns, billing button count, scan receipt-card shape — to eliminate CLS.
- **De-duplicate the category-badge tone logic** (three copies) into one `components/brand` helper so dashboard and activity stay consistent.

### Accessibility
- **Add `aria-live` to every server-action result** (onboarding, profile, scanner error, activity filter count) — the recurring WCAG 4.1.3 gap. Fix the shared non-live `<p>` pattern once.
- **Make the desktop customers row keyboard-operable** (WCAG 2.1.1) and expose `aria-selected` — currently the primary scan workflow is mouse-only at desktop widths.
- **Move focus to the first error on failed submits** and stabilize heading outlines (mobile launch tabs, the scan h1→h3 skip, empty-state/error-boundary levels).
- **Add a merchant-voice `app/app/not-found.tsx`** so `notFound()` keeps merchants inside the workspace with a path back.
